# 认证与用户管理

[文档索引](README.md)

## 认证

认证保持简单。

### 服务端初始化

服务端部署后，当 SQLite 数据库（`/data/matrius.db`）中没有任何用户时：

```text
管理员访问服务端
    ↓
创建第一个管理员账号
    ↓
保存管理员账号
    ↓
初始化入口永久关闭
```

只有第一个管理员可以通过初始化流程创建。一旦存在用户，该入口不可再次使用。

**注意区分**：这是服务端初始化，与客户端的首次启动无关。客户端首次打开**不需要**创建管理员，直接进入本地模式即可。

### 创建用户

管理员打开 Web 端 `/admin`，使用管理员账号单独登录后创建用户。「工具测试」栏可对当前部署的 `web_search` / `web_fetch` 发起真实调用，检查上游、代理和正文提取是否正常；它使用 admin scope，与聊天账号的联网额度互不影响。

```text
填写用户名
    ↓
初始密码设为 `<username>@123`
    ↓
哈希后保存
    ↓
仅本次返回初始密码
```

管理页使用 `/api/admin/auth/login` 签发的 admin scope 会话，与「设置 → 账号」的普通登录互不影响；管理员也可在该页面退出管理会话。禁止保存明文密码。初始密码只展示一次。

### 首次登录

新用户首次登录必须修改密码。

新密码只要求非空且不超过 256 个字符，不能与当前密码相同；确认密码必须一致。登录与改密的每个密码输入框都有独立的可视开关，划线眼表示隐藏，普通眼表示明文显示。

建议的用户字段：

```text
id
username
password_hash
is_admin
must_change_password
created_at
updated_at
```

流程：

```text
用户登录
    ↓
must_change_password = true
    ↓
强制修改密码
    ↓
must_change_password = false
    ↓
进入对话
```

### 管理页

管理页提供：

```text
用户列表（可搜索）
全部 / 管理员 / 待改密码 / 已停用统计
创建用户（可选管理员）
重置密码（一次性显示并复制）
停用 / 启用用户（不提供删除）
```

管理页有独立的登录入口和会话范围，不复用普通用户的会话。管理登录页与用户管理工作台分开：未登录时只显示管理员登录卡片，登录后进入完整工作台。停用自己或最后一个管理员由服务端拒绝，前端也禁用停用当前管理员的按钮。

重置密码应当：

```text
重置为 `<username>@123`
设置 must_change_password = true
仅本次返回新密码
```

在明确需要之前，不要引入：

```text
RBAC
组织
租户
复杂权限系统
```

## 同一地址的账号功能开关

Web 设置中「账号」是独立分组，排在设置导航最上方：账号页使用现有 `/api/auth/login`、`/me`、`/change-password`、`/logout`。侧栏底部未登录时显示「未登录」，点击进入账号设置页；登录入口位于该页，按钮打开登录弹窗，登录成功返回的账号决定是否进入强制改密步骤。首次密码修改完成后才获得功能能力。浏览器登录使用服务端设置的 HttpOnly、SameSite=Lax 持久 Cookie（HTTPS 下加 Secure，Max-Age 400 天，每次 `/me` 校验时滑动续期），JS 无法读取 token；页面加载时带 Cookie 请求 `/me` 还原登录态，不缓存用户名、功能权限或密码。其他页面重新获得可见性时重新验证，网络失败时隐藏受控功能；退出登录或会话被撤销后 Cookie 立即失效。服务端同时保留 Bearer token 能力，供非浏览器的 API 调用使用。Mock 不读取真实登录状态。

账号页还提供「启用网络工具」开关，默认开启，按用户保存在当前浏览器，仅在验证通过且完成首次改密后显示。开关控制下一轮回复是否注册 `web_search` / `web_fetch`，关闭后仍可使用模型与本地数据，不会清空已有对话或同步数据。

账号登录并完成首次改密后，聊天切换到当前账号的云端仓储，通过 REST 读写服务端，不导入、合并或缓存浏览器本地工作区。退出恢复本地工作区，切换账号重新加载对应数据。后台验证期间保留已有账号身份以避免反复卸载工作区；验证失败不回退到本地。模型配置和 API key 始终在本机，登录前后及不同账号共用。账号页不再提供后台双向同步与同步范围选择。详见[存储与数据](data.md)。

功能清单唯一事实源为 `server/app/features/registry.py`：新增功能必须登记，登记后对所有完成首次改密且未停用的账号生效，没有预览白名单、用户名名单或 `isAdmin` 例外。授权只来自服务端认证状态，不接受客户端传入的用户名、header 或 query。账号必须由已有管理员正常创建，不存在默认测试密码或登录后门。

登录响应和 `/api/auth/me` 的 `user.features` / `features` 是当前账号可用的功能 ID。`GET /api/features` 返回该账号可用的功能说明，未登录返回 401。认证和功能响应设置 `Cache-Control: no-store`，每次请求独立校验当前用户和账号停用状态。

客户端使用统一 `useFeature(id)` / `<FeatureGate name="...">` 控制入口，不在页面判断用户名；设置分类和搜索同步过滤，受控路由直达也重新验证权限。当前登记项为 `files`：登录并完成首次改密后可使用文档工具与资料库。

### 从开发到上线

1. 新功能在 `server/app/features/registry.py` 登记，UI 入口、设置搜索、路由及服务端接口都接入同一功能 ID 的控制。已有行为替换应保留原分支，不能仅隐藏新增按钮。
2. `npm run dev` 用本机 Web/API 与隔离的开发数据完成验证；未验证的功能不要提交或部署。
3. 验证通过后提交到 main，由手动 CD 发布。部署健康检查通过后，功能对所有已登录且已改初始密码的账号立即开放；不存在分账号灰度。
4. 如需撤回，移除登记项及相关入口后重新部署；服务端下一次请求立即按当前代码校验，客户端在刷新或重新可见后更新入口。

登记项只来自 `server/app/features/registry.py`，没有额外的发布清单或手工同步步骤。正式账号共用运行代码和进程；本机开发 API 运行自己的代码，数据位于 `server/.data`，与正式服务器完全隔离。功能开关不隔离公共代码错误或性能影响；正式库的结构迁移需先在本地空库验证、保持向前兼容；每次部署都会自动执行迁移（见[服务器部署](deployment.md#数据库迁移与备份)）。

### 新功能接入示例

功能清单的 key 与 Feature.id 必须一致：

```python
FEATURES["new-feature"] = Feature("new-feature", "新功能名称", "用户可理解的功能说明。")
```

新增入口使用统一门控；替换旧行为时根据 `useFeature("new-feature")` 选择新旧分支，保留普通账号原有行为：

```tsx
<FeatureGate name="new-feature"><NewFeaturePanel /></FeatureGate>
```

对应接口必须独立校验，不要把显示隐藏当成权限：

```python
@router.post("/new-feature")
async def new_feature(ctx: AuthContext = Depends(require_feature("new-feature"))):
    ...
```

功能授权只由服务端集中判断，业务组件和接口不各自判断用户名。未登记的功能默认拒绝；已有功能的大改动应使用新的功能 ID 做新旧分支，不能直接改变所有用户共用的实现并期望开关自动隔离。
