# 多账户并发压测与容量建议（2026-10-27）

本次压测回答的是「很多账户同时读写时，单机 API 能稳定跑到多少」，不是单账户内多标签页的并发，也不是完整用户旅程。结论只适用于当前部署形态：单 Uvicorn worker、进程内缓存与限流、SQLite WAL、本地文件存储。生产容量必须在目标服务器上复测。

## 结论

本机（WSL2，Intel Core Ultra 7 255U，14 个逻辑 CPU）上的稳定点：

- **500 个账户**同时以读 120 rps、混合 100 rps、写 60 rps 运行时，全部达标；P95 分别为 21.5 / 9.2 / 10.9 ms，API 进程 CPU 56% / 47% / 37%（单核百分比），客户端 CPU 仅 10%–21%。
- 继续加压后，**读取约 140–175 rps、混合约 150 rps、写入约 100–135 rps** 接近单进程上限；再往上主要是排队，P95 会从几十毫秒涨到数秒，健康检查也会被拖慢。
- 多账户场景下，**瓶颈是聚合请求速率，不是账户数本身**。500 个账户每人 0.24 次读/秒与 5,000 个账户每人 0.024 次读/秒，对 API 的压力相同；账户数增长主要影响数据库体积、认证查询工作集和登录突发。
- 每账户限流（读 240/分钟、写 120/分钟）远高于服务端总容量。500 个账户即使都只用到限流的一小部分，也能把单机打满。**限流保护的是账户间的公平，不是服务器本身**；需要额外的全局准入控制或降载策略。

## 测试方法

压测脚本为 `server/scripts/benchmark.py`，本轮新增和使用了 `pinned` 模式：

- **账户固定（pinned）**：每个虚拟账户绑定自己的令牌和会话，工作线程不轮换账户。这样测到的是「很多账户同时在线」，而不是所有请求随机落到少数热账户。
- **每账户限速**：`Pacer` 给每个账户独立配额，请求按 `1/rate` 间隔发送，并把账户相位错开，避免同一时刻全体起跑。服务端变慢时，节拍器不会追赶积压，观测到的速率反映真实背压。
- **每账户并发 K**：同一账户可同时有 K 个在途请求（K ≤ 10），用于模拟单账户多标签页/多端；不同账户互不阻塞，用于观察公平性。
- **公平性**：统计每个账户请求延迟的 P95，再看这些 P95 的中位数、P95、最大值和「最大值/中位数」。
- **健康探测**：每 100 ms 请求一次 `/api/health`，记录延迟和失败数，观察饱和时控制面是否还能响应。
- **资源采样**：从 `/proc/<pid>/stat` 和 `/proc/<pid>/status` 采样 API 进程 CPU、RSS，并记录 WAL 大小；客户端进程同样采样，用来判断结果是不是被压测机自己限制。
- **跨租户隔离**：随机取 10 对账户，用 A 的令牌读/写 B 的会话，期望全部 404。

负载构成：

- 读取交替调用「会话列表」和「带消息的会话详情」；混合场景为 80% 读、20% 写；纯写为发送一条约 1 KB 的用户消息。
- 种子数据：500 个账户、5,000 个会话、10,000 条消息；每个账户 10 个会话，第一个会话有 20 条消息。Pinned 模式的 K 个 worker 使用不同会话，避免撞上已知的同会话写入竞争。
- 真实 HTTP、真实 Bearer 会话认证、真实限流；临时 SQLite 文件由 Alembic 迁移创建；单 Uvicorn worker、无 reload。为排除登录限流，种子阶段直接创建会话，CRUD 阶段不重复登录。
- 每档持续 8 秒，不计用户思考时间，不重试。RPS 分母包含收尾时间。

**压测客户端限制**：客户端和服务端在同机、单进程运行。200/500 账户的高速率档中，部分结果的客户端 CPU 达到 90%–100%，这些档位是**压测机先饱和**，不能当作服务端上限。下文表格标出了客户端 CPU；判断有效性的标准是客户端 CPU 明显低于 100%，或服务端 CPU 已接近单核饱和。

## 读吞吐悬崖与修复

压测最初复现了一个反直觉现象：并发从 1 增加到 10，数据库直读吞吐反而从约 337 rps 掉到约 50 rps。逐查询拆解后，瓶颈集中在会话消息查询（0.6 ms → 147.6 ms）。排查排除了 WAL、journal 模式、tmpfs、mmap、immutable、shared cache、长读事务、GC、切换间隔和绑核。

根因是当前运行环境里的 **CPython GIL + sqlite3 逐行释放/重新获取 GIL + WSL2 调度延迟** 形成的车队效应：

- 原生 sqlite3 单线程 19,791 rps，10 线程只有 48.2 rps；
- 多进程则从 15.6k 扩展到 47.8k；
- 单连接 + Python 锁在 10 线程下仍有 9,340 rps；
- 与数据库无关的 `os.stat` 从 944k 降到 24.5k，`sha256` 从 319k 降到 23.7k，说明这是通用调度问题，不是 SQLite 写锁。

因此，**在 SQLite 上开很多 aiosqlite 连接会适得其反**。修改如下：

1. `app/db.py`：SQLite 文件库默认连接池改为 `pool_size=2, max_overflow=0`；非 SQLite 保持 5/10；两个值都可通过 `DB_POOL_SIZE` / `DB_MAX_OVERFLOW` 覆盖。
2. SQLite 关闭 `pool_pre_ping`：本地文件连接不会像网络数据库那样断开，每次 checkout 多一次查询没有收益。
3. `app/auth/dependencies.py`：认证完成后释放数据库连接。否则一次长达数十秒的网页抓取会一直占着池，2 个连接很快被耗尽，其他请求全部排队。
4. 文件上传/下载/删除，以及文件读取/正则搜索，在进入慢 I/O 前显式 `await db.close()`；需要改数据时再按 id 重新加载。

同一轮、同一阶段的对比（每账户并发 10/25，单位 rps）：

| 场景 | 旧池 5/10 | 新池 2/0 | 池 1/0 |
| --- | --- | --- | --- |
| 读取 c=10 / c=25 | 49.1 / 48.0 | 175.3 / 187.3 | 203.5 / 193.2 |
| 混合 c=10 / c=25 | 65.0 / 63.9 | 174.0 / 169.8 | 171.9 / 152.6 |
| 写入 c=10 / c=25 | 119.0 / 118.2 | 130.0 / 133.6 | 144.6 / 108.3 |

`1/0` 的读略快，但上传、下载或慢查询期间没有备用连接；`2/0` 在保持吞吐的同时留出一条连接，作为默认值更稳。

**重要限制**：这个悬崖与宿主机/虚拟化调度有关。在其它 Linux 内核或裸金属上，2 个连接未必是最优，但它是安全的保守默认值。上生产前应使用同样的 `pinned` 模式在目标机复测，再决定是否调大。

## 隔离、错误与健康

- **跨租户隔离**：10 对账户的 10 次跨账户读、10 次跨账户写全部返回 404，没有越权成功。
- **服务端错误计数**：`database is locked`、`QueuePool limit`、`UNIQUE constraint failed`、`MissingGreenlet` 均为 0。压测期间没有出现连接池耗尽或 SQLite 写锁超时。
- **健康检查**：稳定点 P95 8–38 ms；饱和点可到 2.7–3.7 s。健康接口能返回 200 不代表还有容量，监控应同时看 API P95、数据库等待和队列长度。
- **测试基线**：修改后后端全量 166 项测试通过（含新增的文件上传/下载/删除与跨账户隔离回归测试）。

## 已知风险（压测未覆盖或刻意绕开）

1. **同一会话并发写入仍可能失败。** 两个请求可能读到相同的 `max(position)`，触发 `(conversation_id, position)` 唯一约束；回滚后再访问 `ctx.user.id` 还可能因 ORM 属性过期抛出 `MissingGreenlet`，把冲突变成 500。Pinned 模式让同一账户的 K 个 worker 使用不同会话，因此本轮吞吐数据不包含这个竞争。单账户并发上限是 10，但如果这 10 个请求可能写同一个会话（多标签页、重试、后台同步），仍需在发消息路径上做冲突重试或按会话串行化。
2. **登录密码校验阻塞事件循环。** `verify_password` 在 async 路由中同步执行 Argon2；此前 10 个不同账户同时登录，登录 P95 约 668–734 ms，同期健康请求最慢约 551–574 ms。登录不频繁，但突发登录会拖慢所有请求。应移到有并发上限的 `asyncio.to_thread`。
3. **单 worker 是硬约束。** 缓存、限流、工具并发信号量都是进程内状态，不能直接开多个 Uvicorn worker。横向扩容必须先引入共享状态（如 Redis）并改数据库。
4. **SQLite 单写者。** 所有写事务串行；写入上限约 100–135 rps。数据库和 API 必须同一台机器、本地块存储，不能用 NFS。
5. **没有全局准入控制。** 限流是按账户的，聚合流量超过单机容量时只会排队。对外暴露大量账户时，建议增加全局并发上限或基于队列延迟的降载。

## 服务器配置要求

以下按当前单进程 + SQLite 架构给出。CPU 百分比是「一个核的百分比」；事件循环仍是单线程，因此**单核性能比核数更重要**。多出来的核主要留给 aiosqlite 线程、Caddy、Web 容器、Docker 和操作系统。

| 规模 | 稳定负载目标 | CPU | 内存 | 磁盘 | 网络 |
| --- | --- | --- | --- | --- | --- |
| 开发/试用（≤50 账户） | 读 100、混合 80、写 40 rps | 2 vCPU | 2 GB | 20 GB SSD | 10 Mbps |
| 小规模生产（≤200 账户） | 读 120、混合 100、写 60 rps | 2–4 vCPU | 4 GB | 40–80 GB SSD/NVMe | 100 Mbps |
| 500 账户（本轮稳定点） | 读 120、混合 100、写 60 rps | 2–4 vCPU | 4 GB | 80 GB SSD/NVMe | 100 Mbps |
| 接近上限（200 rps 读 / 150 混合） | 不保证 P95 | 4 vCPU | 8 GB | 80 GB+ | 100 Mbps+ |
| 超过单机上限 | 需要改架构 | 4–8 vCPU | 8–16 GB | 200 GB+ | 1 Gbps |

补充说明：

- **内存**：本轮 API 进程 RSS 为 133–161 MiB，另含 64 MiB 进程内缓存上限、上传/抓取缓冲、Caddy 和 Web 容器。2 GB 是下限，4 GB 更稳妥；如果同机还跑模型中继（Node，200 条并行 SSE 时约 83 MiB），建议 4–8 GB。
- **磁盘**：实测 500 账户、5,000 会话、10,000 条消息的数据库约 17 MB，即约 1.7 KB/条消息。按每用户 1,000 条消息估算约 1.7 MB/用户；10,000 用户约 17 GB。部署脚本保留 10 份 SQLite 全量快照，另有 14 天文件备份，磁盘要按「数据库 × 5–10 + 文件 + 系统」预留，或把备份放独立卷/远端。用户文件配额上限是 512 MiB/账户，这是上限不是均值，必须监控实际用量。
- **网络**：稳定点 120 读/秒中约一半是会话详情，单条约 20 KB（20 条 1 KB 消息），出口约 1–2 MB/s，即 10–20 Mbps；100 Mbps 端口足够。真实消息更长时应按字节数重算。模型 SSE 是独立的中继进程，本轮未测其带宽，只在模拟条件下验证过 200 条并行流可完成，且没有测出上限。
- **磁盘 IOPS**：写入稳定点 60 rps、上限约 100–135 rps，任意本地 SSD 都足够；不要用网络文件系统承载 SQLite。
- **可用性**：单机、单 API 容器、SQLite 意味着没有应用层高可用。故障恢复依赖快照和重启；如需多机热备，必须换 PostgreSQL 并解决进程内状态共享。
- **系统**：Linux + Docker Compose，一个 API 容器、一个 Caddy、一个 Web 容器；API 不要开多 worker。容器内存建议给 API 留 1 GB 上限，给整机留 25% 余量应对突发和备份。

### 什么时候必须扩容/改架构

- **持续读 > 150–175 rps，或混合 > 150 rps**：已经接近本机上限，P95 会进入数百毫秒到数秒。加 CPU 核数帮助有限，因为 Python 事件循环是单线程；需要多 worker + 共享缓存/限流 + PostgreSQL（或按账户分片）。
- **持续写 > 100–135 rps**：SQLite 单写者到顶，必须换 PostgreSQL。
- **账户数 > 1,000 且登录突发明显**：同步 Argon2 会阻塞事件循环，先修登录，再评估多 worker。
- **需要多机/高可用**：SQLite 和进程内状态都不支持，属于架构变更，不是加机器能解决。
