# 本机并发容量测试（2026-10-24）

> 多账户场景的稳定点、单机上限、SQLite 连接池修复和服务器配置要求见 [多账户并发压测与容量建议](performance-multiaccount.md)（2026-10-27，Linux/WSL2）。本文是更早的单账户/轮转压测记录，保留作对照。

本次是容量摸底，不是生产 SLA。模型中继在模拟上游条件下通过 200 条并行 SSE 流；FastAPI 在 10 个持续并发请求下有较好延迟，50 个以上开始明显排队。更重要的是，当前消息写入存在可复现的并发冲突错误，不能据此承诺生产可稳定服务多少用户。

## 条件与范围

- Windows 11，本机 Intel Family 6 Model 141、12 个逻辑 CPU，Python 3.12.15。没有测量 CPU 利用率、API 内存曲线、磁盘 IOPS 或生产服务器配置。
- 独立临时磁盘 SQLite，运行真实 Alembic 迁移，WAL 和现有连接池配置；单 worker Uvicorn，无 reload。不是内存数据库或 ASGI 直调。
- 500 个合成账号、5,000 个会话、10,000 条种子消息，每条约 1 KB。每个账号有 10 个会话，其中一个有 20 条消息；写入阶段数据继续增长。
- 真实 HTTP、真实会话认证查询、原有用户限流和 INFO 请求日志。为排除登录限流对 CRUD 容量的影响，初始化时直接建立合成会话，CRUD 不重复做密码验证。
- 并发 1 / 10 / 25 / 50 / 100 / 200，每档持续发起请求 8 秒，然后等待在途请求结束；没有用户阅读等待时间，没有重试。RPS 分母包含收尾时间，延迟统计包含错误响应。
- 读取交替调用会话列表和带消息的会话详情；混合为 80% 读取、20% 消息写入；纯写入为保存用户消息。账号轮转不保证同一账号的慢请求一定已经结束。
- 测试客户端和服务端同机，绕过 Caddy、TLS、容器与真实网络；短时间闭环负载存在局限，没有做数小时稳定性测试。
- 实际前端目前还有本地 IndexedDB 与账号后台同步路径；这里测的是后端 API 能力，不能当成逐 token 同步或完整用户旅程测试。

主结果：[benchmark-results.json](benchmark-results.json)。另外重跑了冲突与登录探针，见 [benchmark-contention-results.json](benchmark-contention-results.json)。初始化账号、令牌、临时数据库和日志不进入报告，结束后清理临时测试目录。未访问正式服务器、真实账号、模型或外部搜索服务。

## FastAPI 结果

表格为「成功请求/秒；P95 毫秒」。P95 表示 95% 的请求在该时间内结束。

| 持续并发请求 | 读取 | 混合读写 | 纯消息写入 |
| --- | --- | --- | --- |
| 1 | 159.74；7.72 | 126.29；10.37 | 96.13；14.20 |
| 10 | 221.20；89.18 | 204.74；91.38 | 130.61；199.95 |
| 25 | 168.16；422.14 | 156.24；498.21 | 139.57；499.92 |
| 50 | 149.66；928.32 | 126.36；1,083.54 | 108.29；1,356.98 |
| 100 | 138.87；2,019.54 | 103.75；2,560.87 | 98.02；2,717.21 |
| 200 | 122.96；4,213.91 | 110.94；4,577.71 | 96.53；5,190.76 |

读取与混合场景本轮没有错误；25 并发纯写入为 1,168 次成功、3 次 HTTP 500。其他纯写入档位本轮没有错误，不能理解成增加并发可以消除错误。首次探索测试也出现了少量纯写入 500，失败与调度时机有关。

10 个持续并发附近吞吐较高；继续增加并发主要增加等待。200 并发「请求最终结束」不等于交互体验合格，更不等于适合 200 人同时操作。

## 发现的稳定性问题

1. **同一会话并发写入会失败。** 主测试的 25 条同时写入有 17 成功、8 次 500；独立复测为 7 成功、18 次 500。这是刻意制造的同一会话竞争场景，不是普通多用户错误率，但说明多标签页、重试或后台同步竞争需要处理。
2. **日志确认是消息位置唯一约束冲突叠加 `MissingGreenlet`。** 两次请求可能读到相同 `max(position)`，同时写入下一个位置，触发 `(conversation_id, position)` 唯一约束。`create_message` 回滚后又访问 `ctx.user.id`；SQLAlchemy 回滚会使 ORM 属性过期，异步环境下的隐式重新加载又抛出 `MissingGreenlet`，原本应转换的冲突成了 500。这个因果链由日志、代码及 [SQLAlchemy 回滚文档](https://docs.sqlalchemy.org/en/21/orm/session_basics.html#rolling-back)共同支持。日志没有观察到 `database is locked` 或连接池超时，不能把本轮 500 归因于它们。日志中的异常字符串可能重复出现，`server_error_counts` 是文本匹配次数，不是失败请求数。
3. **同版本修改探针本次正常。** 两轮都是 25 次请求中 1 次成功、24 次 409，revision 从 1 变为 2。该样本没有观测到覆盖，但代码仍是先检查再更新，不能据一次调度结果证明所有写接口的乐观并发都是原子的。
4. **登录突发拖慢其他请求。** 10 个不同账号同时登录均成功，登录 P95 约 668–734 ms，同时健康请求最慢约 551–574 ms。密码校验在 async 路由中同步执行；结合代码判断会阻塞事件循环。这次只测同一来源 IP 允许的 10 次突发，没有关闭登录限流来测更高流量。

这些后端缺陷本次已定位和记录，尚未修改生产实现。应先解决消息位置分配和回滚错误处理，再重跑并发测试；登录密码运算应移到有并发上限的工作线程，避免挤占事件循环。不要仅靠增加 Uvicorn workers：本项目限流与缓存是进程内状态。

## 模型 SSE 中继

使用真实 `scripts/model-proxy.cjs`，在隔离 VM 内替换出站 HTTP 目标和 DNS，使其连接本机模拟模型；生产模块和私网校验没有修改。模拟上游每 100 ms 发一帧，50 帧后发送 DONE，持续约 5 秒。客户端、代理、上游在同一个 Node 进程中，RSS 也是三者合计。

| 并行 SSE 流 | 完整结束 / 错误 | 首块 P95 | 整轮 P95 | 进程 RSS |
| --- | --- | --- | --- | --- |
| 1 | 1 / 0 | 115 ms | 5.45 s | 50.9 MiB |
| 25 | 25 / 0 | 144 ms | 5.48 s | 56.7 MiB |
| 100 | 100 / 0 | 190 ms | 5.53 s | 68.1 MiB |
| 200 | 200 / 0 | 230 ms | 5.58 s | 82.6 MiB |

每条成功流收到 50 个内容帧和 DONE。结果见 [benchmark-relay-results.json](benchmark-relay-results.json)。这证明短时间模拟流量下 200 条流可完成，**没有测出中继上限**。没有覆盖真实模型延迟、TLS、跨网抖动、慢客户端背压、长时间流、断连恢复或模型商并发额度。

## 能供多少用户

并发 HTTP 请求数、同时生成的对话数、在线用户数和注册账号数是四个不同量。这次没有完成带工具和真实模型的端到端用户负载测试，不能给出可靠的全站用户容量。

作为后续验证的保守目标，可以先按 20–40 次 FastAPI 请求/秒设计负载，保留本机饱和吞吐的余量。若每个活跃用户平均每 5 秒产生 1 次 API 请求，则按 `用户数 = 请求/秒 ÷ 人均请求/秒` 算出约 100–200 个活跃用户；若每人每秒请求一次，则只有约 20–40 个。**这是工作负载假设下的容量预算，不是已验证的用户规模，而且要先修复上述写入缺陷。** 正式值必须在目标服务器上验证真实登录、同步、工具和模型流量。

联网工具可能更早排队：现代码搜索全局并发 4、网页读取全局并发 4、上传处理全局并发 2。搜索和读取的缓存命中与上游耗时会显著影响可服务人数，本次没有向外部网站压测。SQLite 本身也只允许一个同时进行的写事务，见 [SQLite 事务文档](https://www.sqlite.org/lang_transaction.html)。
